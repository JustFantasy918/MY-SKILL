## B. 自动测试**抓不到**但必须人工查的项目

### B1 语义 / 逻辑类

- [ ] **方法论是否自洽**：第一性原理章节和操作章节是否有矛盾？
- [ ] **前后结论是否一致**：同一概念在不同文件里说法是否统一（如"宏观维度"在 A 文件说三个，B 文件说四个）
- [ ] **原话 vs 媒体解读 vs 框架推演**是否清晰分节标注？
- [ ] **时效性陈述**（如"2026 年最新观点"）是否真的有来源日期？

### B2 设计 / 用户体验类

- [ ] **场景索引完整吗**：用户常问的 5-10 类问题是否都能被 SKILL.md 的索引命中？
- [ ] **触发词足够具体吗**：是否能区分"问 skill 内容"vs"验收 skill"？
- [ ] **新手能否快速上手**：第一次读 SKILL.md 能不能在 30 秒内知道怎么用？
- [ ] **失败处理**：取数失败、文件不存在等异常路径有没有指引？

### B3 跨文件一致性（人工比自动更可靠）

- [ ] **同一概念术语统一**：如"流动性"在不同文件里是不是同一个意思
- [ ] **编号体系统一**：水位线编号、维度编号、案例编号有没有跨文件冲突
- [ ] **版本号同步**：主 skill 升版本时，依赖它的其他 skill 是否同步更新

## C. 工具自带的检查不能替代

### C1 跑通 ≠ 正确

T6 让代码块跑通只证明语法/环境正确。**业务逻辑对不对**需要：
- 拿真实数据做端到端演练
- 对比脚本输出 vs 人工判断
- 在用户场景中实际使用

### C2 PASS 不代表无需改进

一个 skill 全 PASS 也可能：
- 测试覆盖度本身不够（如 T4 没提供场景文件就跳过）
- 关键词列表与实际领域不符（如默认 marks 是"原话/媒体解读/框架推演"，对别的 skill 可能不适用）
- 真正的问题在 T1-T8 之外的维度（如哲学性矛盾）

## D. 出问题时的高效排查顺序

1. **看 FAIL 的 detail 提示**：通常直接定位到行号或文件名
2. **跑 `--quiet` 模式**：只显示失败项，避免噪音
3. **如果 T2 报悬空引用**：用 grep 在目标文件搜引用中的关键词
4. **如果 T6 报代码失败**：单独跑该代码块，加 print 调试
5. **如果 T7 报数字可疑**：人工核对，但先看脚本给出的可疑文本上下文
6. **如果 T8 报官方校验失败**：跑 `package_skill.py` 看完整输出（脚本只截了最后一行）

## E. 与官方 package_skill.py 的分工

| 维度 | qa_check.py | package_skill.py |
|---|---|---|
| 性质 | 通用、可配置 | 内置、单一标准 |
| 检测内容 | 结构 + 引用 + 内容 | 结构 + 校验器内部规则 |
| 可扩展 | ✅ 加新测试层 | ❌ |
| 是否发布门槛 | ❌ 是辅助 | ✅ 是 |
| 跑通建议 | **每次改完跑** | **发布前必跑** |

**结论**：两者互补，不替代。建议发布前两者都跑。
